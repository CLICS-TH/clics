### ตัวเลขนี้แปลว่าอะไร และไม่แปลว่าอะไร

`ICC = var_between / (var_between + var_error)` ดังนั้น 0.75 ต้องการ `var_between ≥ 3 × var_error`
เมื่อ SD ระหว่าง episode (2.44) ต่ำกว่าที่ต้องการ (4.66) **การเพิ่มจำนวนผู้ประเมินบน cohort ชุดนี้
ไม่ทำให้ ICC ตีความได้** ไม่ว่าจะเพิ่มถึง 3 คนตามเป้าหรือมากกว่านั้น เพราะข้อจำกัดไม่ได้อยู่ที่
จำนวนผู้ประเมิน **การคัด cohort จึงต้องมาก่อนการนัดหมายผู้ประเมิน ไม่ใช่ตามหลัง**

สิ่งที่ยัง **ไม่** สรุปได้จากตัวเลขชุดนี้:

- ไม่ได้แปลว่าผู้ประเมินให้คะแนนไม่ตรงกัน สิ่งที่วัดได้คือเขา **ไม่แยกความต่างระหว่าง episode**
  คนละเรื่องกับความไม่ตรงกัน และต้องไม่เขียนสลับกัน
- n = 5 episode, ผู้ประเมิน 2 คน, error SD ประมาณจาก 2 episode เท่านั้น ทุกค่าข้างบนเปราะ
  `gate.measurable` เป็น `true` ได้เพราะมี multi-rated episode พอดี 2 ชุด ให้รายงาน n ควบทุกตัวเลข
- ไม่ได้แปลว่า incumbent evaluator ผ่านหรือไม่ผ่าน G0.5 — G0.5 ยังไม่เคยรัน

รูปแบบนี้ตรงกับสิ่งที่พบในฝั่งโมเดล: held-out split n = 8 ได้ ICC 0.436 เพราะ cohort แคบ ไม่ใช่เพราะ
โมเดล (`METHODOLOGY-local-vs-sonnet.en.md` §7) ทั้งสองฝั่งชี้กลับไปที่ corpus เดียวกัน

## 4. รอบให้คะแนนอย่างอิสระและปกปิด

- [ ] ฝึก rubric ด้วย **ชุดสอน** ให้เสร็จก่อนเปิดชุดวัด ไม่แจกคะแนน AI หรือคำตอบเป้าหมายของชุดวัด
- [ ] แต่ละคนอ่านพฤติกรรมแพทย์ พร้อม reflection ที่ตรวจครบแล้ว ให้ D1–D7 เป็นจำนวนเต็ม 0–5
  เขียนเหตุผลอ้างตำแหน่งหลักฐานในช่อง notes (รวมสูงสุด 4,000 ตัวอักษร) และเลือกความชัดเจน
  ของ anchor ราย domain: `clear / moderate / ambiguous`; เว้นว่างคือ missing ไม่ใช่ clear
- [ ] ไม่หารือคะแนนกับคนอื่นระหว่างวัด ไม่ใช้ AI tutor; หากสงสัย identifier ให้กดหยุดและรายงาน
  ตำแหน่ง/ชนิดข้อมูลโดยไม่คัดลอก identifier การรายงานนี้ไม่ส่งคะแนน
- [ ] ตรวจครบ 7 domains และ confirmations ทั้ง 5 ข้อก่อน submit รวมข้อประเมินอย่างอิสระ
  คะแนนส่งแล้วแก้ซ้ำผ่าน scoring API ไม่ได้ (`409 Already scored`)
- [ ] **กำหนดวิธีปิดคะแนนทั้งชุดก่อนเริ่ม:** ระบบปกปิด AI/peer score จนคนนั้น submit แต่เผยทันที
  หลัง submit **แต่ละ PLE** ไม่ได้รอทุกคน/ทั้ง cohort จบ การเห็น feedback จาก PLE แรกอาจเปลี่ยน
  วิธีให้คะแนน PLE ถัดไปได้ ให้ทีมวิจัยกำหนดวิธีเก็บและตรึง draft scores ทั้งชุดอย่างปลอดภัยก่อน
  submit หรือมีการควบคุม cohort-wide reveal ที่ตรวจแล้ว; ยังไม่มี workflow นี้สำเร็จรูปใน repo
  ไม่ใช้ screenshot/download transcript เป็นวิธีเก็บ draft
- [ ] เมื่อทุกคนปิดคะแนนแล้ว ผู้ประสานงานจึงเปิดการเทียบคะแนนและอภิปราย anchor
  เก็บคะแนนอิสระเดิมไว้; consensus หลังอภิปรายเป็นผลอีกชุดหนึ่ง ไม่เขียนทับ baseline

| [หน้า ICC](https://audit-dashboard-rouge.vercel.app/admin/icc), `GET /admin/icc` | รายงาน AI–mean human ต่อ PLE, จำนวน raters/PLE, ชุดถึงเป้า และ inter-auditor; ตรวจ cohort จริงก่อนใช้ |
| `GET /oversight/icc/three-way` | analyst/ethics/superadmin: แยก incumbent–human, candidate–human, candidate–incumbent พร้อม verdict; shadow scores ไม่ส่งให้ auditor |
| `GET /oversight/rater-spread` | ดูการกระจายคะแนนและ anchor clarity/missing แบบพรรณนา ไม่ใช่หลักฐานผ่าน gate |
| `GET /admin/export?include_test=true&limit=1000&offset=0` | JSON มีคะแนนรายคนและ evaluator provenance; ไล่หน้าตาม `total/limit/offset` |
| `GET /admin/export.xlsx?include_test=true` | ตารางคะแนนรายคน + `scored_at`, model/prompt/rubric; ตรวจ Notes/truncation |

API paths ข้างต้นต่อกับ backend ของสภาพแวดล้อมที่เลือกและต้องมี role/token ที่ถูกต้อง
URLs ของ UI มาจาก [deployment.md](deployment.md); ไม่ใช่ผลตรวจว่าเข้าได้ในวันจัด workshop

มี CLI อ่าน DB และเขียนรายงานไว้ใน `scripts/calibration/runs/`:

```bash
# ใช้ภายหลังเท่านั้น: backend/.env ต้องชี้ DB calibration ที่ผู้ดูแลตรวจ cohort แล้ว
cd backend
NODE_PATH="$PWD/node_modules" node ../scripts/calibration/three-way.js --include-test --top all
```

คำสั่งนี้ไม่เรียก AI แต่โหลดข้อมูลจาก DB จริง ไม่ใช่ dry-run; **ไม่มีตัวเลือก PLE manifest หรือ
prompt filter** และ `--include-test` รวมข้อมูลเก่าด้วย ใช้ได้เป็น G0.5 report ต่อเมื่อ scope ที่อ่าน
ตรง cohort และ raters ที่ยืนยันว่าเป็นมนุษย์จริง แยก simulated rows ออกแล้ว หาก DB ปะปนยังไม่พร้อม
ต้องเตรียมการคัด cohort ให้ถูกก่อน ไม่เปลี่ยน flags ใน production เพื่อทำให้รายงานดูสะอาด

- [ ] รายงานหนึ่งคู่ต่อหนึ่ง PLE: AI เทียบค่าเฉลี่ยผู้ประเมิน พร้อม n ของ PLE และจำนวนคนต่อ PLE
  ไม่ใช้ `calibrate.js` เป็นรายงานหลัก: มัน pool หนึ่งคู่ต่อ auditor ซ้ำ AI เดิม จึงทำให้ n พอง
  และ default เป็น `--mode rescore` ซึ่งเรียก RIMPL/AI จริง
- [ ] ระบุ ICC(A,1)/ICC(2,1), 95% CI, mean bias, per-domain divergence, missing/exclusions และ
  จำนวนคนครบ/ไม่ครบเป้า; inter-auditor ICC(A,k) ใช้เมื่อยืนยัน fixed panel และแนวคอลัมน์ตรงคน
  ทุก PLE เท่านั้น ถ้าหมุนเวียนคนให้ใช้คำอธิบาย/design ที่ตรงกับ ICC(1,1)
- [ ] ใช้ `verdictFor(result, 0.75)` จาก `backend/src/services/icc.js:281–307`:
  **pass** เมื่อ lower ≥ 0.75, **fail** เมื่อ upper < 0.75, นอกนั้น **insufficient**;
  n < 4 หรือไม่มี variance/estimate เป็น insufficient แม้ point estimate ดูดี
  CI ของโค้ดเป็น Fisher-z approximation (`icc.js:52–68`) ให้ผู้รับผิดชอบสถิติยืนยันวิธีรายงาน
  ตาม protocol; อย่าอ้างเป็น exact interval หรือคำนวณ sample size ย้อนเพื่อเลือกเฉพาะผลผ่าน
- [ ] หาก baseline ยังไม่ผ่าน/ยัง insufficient แจ้งทีมวิจัยพร้อม CI และสาเหตุที่ทราบ
  ไม่เรียก insufficient ว่า fail และไม่รับรอง Model Lock จาก screening หรือค่า ICC จุดเดียว

## ของที่พร้อม และงานที่ยังต้องมีเจ้าของ

**พร้อมใน repo:** scoring form, consent/attestation, multi-assignment, reveal หลัง submit,
privacy-concern reporting, ICC/three-way/rater-spread และ export ตามขอบเขตข้างต้น
มี **synthetic UI fixtures** ใน `scripts/manuals/lib/capture-fixtures.mjs` และ
`scripts/readability/fixtures.mjs` ใช้ซ้อมหน้าจอได้ แต่มีคะแนนจำลองและไม่ได้เป็นชุด anchor
ที่ทีมวิจัยรับรอง ส่วน `scripts/probe/fixtures/` ที่ commit มีเพียง `.gitkeep`;
`build-fixtures.mjs` อ่าน DB และแทนที่ไฟล์เดิม จึงไม่ใช่คำสั่งสร้างชุดสังเคราะห์แบบ offline

**ต้องมีคน:** ทีมวิจัยรับผิดชอบ D24/manifest/design; ผู้ดูแลตรวจ environment, roster และ privacy;
ผู้ประเมินจริงให้คะแนนโดยอิสระ; ผู้รับผิดชอบสถิติสรุป G0.5 และแยกจาก D18

**ช่องว่างเครื่องมือที่ยังเหลือ:** ไม่มี CLI จำกัด G0.5 ด้วย manifest/prompt/human-source;
rater-spread มีสรุป anchor แต่ทดแทนบันทึกเหตุผลรายคนไม่ได้
