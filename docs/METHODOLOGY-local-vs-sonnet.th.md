**ระเบียบวิธีและผลการศึกษา CLICS local-evaluator screening study, 2 – 4 กันยายน 2569**

เอกสารนี้จัดทำขึ้นเพื่อให้เขียนส่วน Methods และ Limitations ของบทความวิจัยได้โดยไม่ต้องคำนวณตัวเลขใหม่
ทุกตัวเลขในเอกสารนี้สร้างซ้ำได้จากข้อมูลที่ commit ไว้แล้ว ด้วยคำสั่ง

```sh
node scripts/probe/report/methodology-figures.mjs          # อ่านด้วยตา
node scripts/probe/report/methodology-figures.mjs --json    # อ่านด้วยเครื่อง
```

ซึ่งอ่านจาก `scripts/probe/report/*.json` ตัวเลขใดที่มาจากเอกสารโครงการฉบับอื่นจะอ้างหัวข้อกำกับไว้ในบรรทัดนั้น
ไม่มีตัวเลขใดถูกคัดลอกมาจากหน้าจอด้วยมือ

**ข้อสรุปหลัก** — screening gate ให้ผล `insufficient` บน held-out split ที่กันไว้ล่วงหน้า:
ICC(A,1) = **0.436** (95% CI 0.000 – 0.873, n = 8) เทียบกับเกณฑ์ 0.75 ที่วัดจาก**ขอบล่าง**ของช่วงความเชื่อมั่น
สิ่งที่มีความหมายจริงคือ**เหตุผล**: ใน split ชุดนี้ ความต่างเชิงสัมบูรณ์ระหว่างสองโมเดลต่ำที่สุดในทั้งการศึกษา

**ข้อจำกัดที่แท้จริงอยู่ที่ชุดข้อมูล ไม่ใช่ที่โมเดล**

## 1. คำถามวิจัยและการออกแบบ

**คำถาม** — โมเดล open-weight ที่ติดตั้งบนเครื่องภายในองค์กร จะทดแทนโมเดลคลาวด์ระดับแนวหน้าในการให้คะแนน
PIS-7 ซึ่งเป็น rubric 7 มิติสำหรับประเมินการให้เหตุผลทางคลินิกของแพทย์ และเป็นเกณฑ์ตัดสินหน่วยกิต CPD ได้หรือไม่

**การออกแบบ** — paired agreement study โมเดลทั้งสองให้คะแนน transcript ชุดเดียวกันด้วย rubric เดียวกัน
แล้วสรุปความสอดคล้องด้วย intraclass correlation บน composite แบบถ่วงน้ำหนัก

**เกณฑ์นี้ไม่สมมาตร และข้อนี้กำหนดว่าผลลัพธ์ตีความได้แค่ไหน** — มติ D18
(`docs/LOCAL-MODEL-ROADMAP.md`, "Settled 2026-08-28") กำหนด gate **สองชั้น** ที่ threshold เดียวกัน:

| gate | เปรียบเทียบกับ | สถานะ |
|---|---|---|
| **Screening** | **โมเดลเดิม** ที่ใช้งานอยู่ | รันได้ทันที — คือการศึกษานี้ |
| **Decisive** | **ผู้เชี่ยวชาญที่เป็นมนุษย์** | ต้องผ่านก่อน Model Lock — ยังไม่เคยรันได้เลย |

เหตุผลที่ระบุไว้ในมติเองคือเหตุผลที่ความต่างนี้สำคัญ:

> screening ปฏิเสธผู้เข้าชิงได้ตั้งแต่ยังไม่มีผู้ให้คะแนนที่เป็นมนุษย์แม้แต่คนเดียว แต่**ไม่มีวันยอมรับได้**
> เพราะโมเดลสองตัวอาจสอดคล้องกันมากและผิดเหมือนกันทั้งคู่

ดังนั้นผลลัพธ์ของ screening จึงเป็นด้านเดียวโดยโครงสร้าง ผล `insufficient` คือผลที่อยู่ในกรอบนั้น
ไม่ใช่การศึกษาที่ล้มเหลว และในทางกลับกัน ไม่ว่าผล screening จะสูงเพียงใดก็ไม่อนุญาตให้นำไปใช้จริงได้

**การควบคุมแบบ pre-registration** — split ยืนยันผลถูกสุ่มและตรึงไว้**ก่อน**การปรับจูนใด ๆ (มติ D13)
เปิดใช้เพียงครั้งเดียวและถูกใช้หมดแล้ว วิธีการอยู่ในหัวข้อ 2 ผลที่ตามมาอยู่ในหัวข้อ 7.1
ซึ่งไม่ใช่ผลที่คาดไว้

**ความไม่สมมาตรข้อที่สอง ระบุไว้ตั้งแต่ต้น** — ไม่มีค่า ICC ใดในโครงการนี้ที่เคยวัดกับผู้ตรวจที่เป็นมนุษย์จริง
ค่า 0.811 ที่มักถูกอ้างถึงสำหรับ evaluator เดิมนั้นวัดกับ **agent-rater จำลอง 3 ตัวที่กำหนดจุดยืนไว้**
(`scripts/soak/gen-auditor-wf.js:30-32`) บน cohort ที่เองก็เป็นชุดที่สร้างขึ้นใหม่หลังชุดเดิมถูกลบ
ตัวเลขเดียวที่เกี่ยวข้องกับมนุษย์จริงคือ ICC −0.315 ที่ n = 5
**reference standard ในการศึกษานี้จึงเป็น "โมเดลเดิม" ไม่ใช่ ground truth** และหัวข้อ 7.2 วัดว่ามันไม่นิ่งเพียงใด

## 2. วัสดุและเครื่องมือ

### 2.1 ชุดข้อมูล

transcript บทสนทนาการเรียนรู้ทางคลินิกระหว่างแพทย์กับ AI ("PLE") จำนวน **26 ชุด** ดึงจากระบบจริง
และผ่าน PII filter ของ production ด้วย `scripts/probe/build-fixtures.mjs` แต่ละ fixture เก็บเฉพาะ
`{ple_id, patient_ref, transcript[]}` โดย `transcript` เป็นลำดับของ `{role, content}` ที่
`role ∈ {physician, assistant}` และ `patient_ref` เป็น null ทั้ง 26 ชุด ความยาว 8 – 35 turn (มัธยฐาน 12)

**fixture ไม่ถูก commit** เพราะเป็นบทสนทนาทางคลินิก และการ de-identify ที่พลาดแล้วเข้าไปอยู่ใน git history
นั้นกู้คืนไม่ได้ สิ่งที่ commit คือ SHA-256 ของแต่ละ fixture ใน `scripts/probe/SPLIT.json`
ซึ่งถูกตรวจซ้ำทุกครั้งที่รัน (`scripts/probe/split.mjs:44-48`) ชุดข้อมูลจึงถูกตรึงไว้แม้ไม่ได้เผยแพร่

(`pis7-weights-08b0cb1a`) ซึ่งไม่เปลี่ยนตลอดการศึกษา

> **มี composite สองแบบในบันทึก และไม่ใช่ตัวเลขเดียวกัน** — log ของ probe พิมพ์ผลรวม d1–d7
> แบบ**ไม่ถ่วงน้ำหนัก** (ช่วง 0–35) ส่วนเครื่องมือตัดสินใช้ composite **ถ่วงน้ำหนัก** 0–100

>
> *หมายเหตุ 2026-10-01:* probe เปลี่ยนมาพิมพ์ composite แบบถ่วงน้ำหนักแล้ว โดยใช้ `compositeOf` และ `icc.js`
> ตัวเดียวกับ production (ผ่าน `scripts/probe/agreement-stats.mjs`) `e2-compare.mjs` จึงอ่านสองรายงานนั้นได้
> 0.735/0.762 ส่วน 0.726/0.765 เหลืออยู่เฉพาะใน log ที่เขียนก่อนวันที่ดังกล่าว

> **prompt หลักยังไม่เคย calibrate ใหม่นับตั้งแต่ครั้งสุดท้ายที่แก้** — การ hash
> `PIS7_EVALUATOR_PROMPT` ที่ทุก commit ซึ่งแตะไฟล์นั้น ให้สามเวอร์ชัน: `35f265977a8c` (1,312 อักขระ)

> การเปลี่ยนครั้งหลังคือ commit ที่ทำให้ระบบสอดคล้องกับ CREC082 ซึ่งใส่ scale 0–5 และ anchor
> รายมิติที่คณะกรรมการอนุมัติเข้าไป — **การเปลี่ยนนั้นถูกต้อง** เพราะ AI กับมนุษย์ที่ให้คะแนนด้วย rubric

> ความสอดคล้องของโมเดลเดิมกับผู้ให้คะแนนใด ๆ บน prompt ที่ใช้จริง จึงยังไม่เคยถูกวัด

ที่พบจากการวัดครั้งแรก: composite ถูกบีบต่ำลง 2.2 คะแนน (บนผลรวม d1–d7 แบบไม่ถ่วงน้ำหนัก 0–35 —
หมายเหตุ 2026-10-01: ไม่ได้เก็บรายงานของการรันนั้นไว้ จึงไม่มีตัวเลขแบบถ่วงน้ำหนัก), d1 อ่อน และมี level shift
เวอร์ชันที่สองเปลี่ยนเครื่องหมายคำพูดในตัวอย่างเป็น single quote ด้วยเหตุผลในหัวข้อ 7.6

**คันโยกหนึ่งในสองตัวไม่เคยทำงานจริง** — ดูหัวข้อ 7.5 ข้อนี้เองก็เป็นผลการศึกษา

## 4. ตัวชี้วัด

**ตัวชี้วัดหลัก** — ขอบล่างของช่วงความเชื่อมั่น 95% ของ ICC(A,1) บน composite ถ่วงน้ำหนัก เทียบกับ 0.75
ใช้**ขอบล่าง** ไม่ใช่ค่าประมาณจุด เพื่อไม่ให้ช่วงกว้าง ๆ ผ่านเกณฑ์ด้วยความบังเอิญ (มติ D19:
`insufficient` เป็นผลลัพธ์ชั้นหนึ่ง แยกจาก `fail`)

**ตัวชี้วัดรอง**

| ตัวชี้วัด | นิยาม |
|---|---|
| ICC(A,1) รายมิติ | ตัวประมาณเดียวกัน คำนวณแยกแต่ละ d1–d7 |
| Σ\|Δ\| ความสอดคล้อง | ต่อ fixture, Σ ของ d1–d7 ของ \|โมเดลทดสอบ − โมเดลเดิม\| — ความต่าง**ระหว่าง**สองโมเดล |
| Σ\|Δ\| ความคงเส้นคงวา | ต่อ fixture, Σ ของ d1–d7 ของ (max − min) เมื่อ**โมเดลเดียว**ให้คะแนนซ้ำ — คือ noise floor |
| parseability | สัดส่วน JSON ที่ถูกต้องตาม PIS-7 ต่อจำนวน**การเรียก** เกณฑ์ ≥ 98% |
| bias | ค่าเฉลี่ยโมเดลทดสอบ − ค่าเฉลี่ยโมเดลเดิม บน composite |
| ขอบเขต Bland–Altman | ค่าเฉลี่ยผลต่าง ± 1.96 SD |

> Σ|Δ| สองตัวนี้ตอบคนละคำถาม และก่อนการเขียนรายงานฉบับนี้ถูกบันทึกไว้ใต้หัวคอลัมน์เดียวกัน
> ความคงเส้นคงวาเป็นตัวกำหนดเพดานว่าความสอดคล้องจะมีความหมายได้แค่ไหน — โมเดลที่ไม่ตรงกับตัวเอง
> ถึง 6 คะแนน ย่อมพิสูจน์ไม่ได้ว่าตรงกับสิ่งใดในระดับ 2 คะแนน

## 5. วิธีทางสถิติ

**Intraclass correlation** — ICC(A,1) แบบ two-way random effects, absolute agreement, single measure
(เทียบเท่า ICC(2,1) ในระบบ Shrout–Fleiss) ตัวประมาณคือ implementation ที่ใช้ใน production จริง
(`iccTwoRater` ที่ `backend/src/services/icc.js:20-72`) โดยไม่ดัดแปลง เพื่อให้ตัวเลขที่อ้างในบทความ
เป็นตัวเลขเดียวกับที่ระบบใช้ตัดสินหน่วยกิตจริง การเลือก absolute agreement แทน consistency เป็นสิ่งจำเป็น
ที่นี่: ผู้ให้คะแนนที่จัดอันดับ episode ได้เหมือนกันแต่ให้คะแนนต่ำกว่าสองแต้มทุกครั้ง ไม่ใช่สิ่งทดแทนที่ใช้ได้

**ช่วงความเชื่อมั่น** — ตัวเลขในรายงานนี้คำนวณด้วย Fisher-z โดย se = 1/√(n − 3) แล้วแปลงกลับและตัดให้อยู่ใน [0, 1]
ซึ่งเป็นวิธีที่ `icc.js` ใช้ในเวลานั้น ตั้งแต่ 2026-10-01 `icc.js` เปลี่ยนไปใช้ช่วงแบบ F ของ McGraw & Wong (1996)
(สูตรเดียวกับ `irr` ใน R และ pingouin) ถ้ารันการวิเคราะห์นี้ซ้ำ ขอบของช่วงจะต่างไปแม้ point estimate เท่าเดิม
และต้องระบุว่าใช้ช่วงแบบไหน ที่ n = 8 ช่วงทั้งสองแบบกว้างโดยโครงสร้าง และการศึกษาออกแบบโดยรู้เรื่องนี้อยู่แล้ว
ดูการคำนวณกำลังทดสอบด้านล่าง ตัวประมาณจะปฏิเสธการให้ผลตัดสินเมื่อ n < 4 (`icc.js:281-308`)

**กฎการตัดสิน** — `pass` เมื่อขอบล่างเกินเกณฑ์ · `fail` เมื่อขอบบนต่ำกว่าเกณฑ์ ·
**`insufficient`** เมื่อช่วงคร่อมเกณฑ์ สถานะที่สามคือหัวใจของการออกแบบ
เพราะแยก "เราวัดได้ว่าไม่สอดคล้อง" ออกจาก "เราวัดไม่ได้"

**กำลังทดสอบ** — `screening-verdict.mjs:138-143` ย้อนช่วงความเชื่อมั่น: กำหนดค่า ICC จริงที่สมมติขึ้น
แล้วค้นหา n ที่น้อยที่สุดซึ่งทำให้ขอบล่างเกินเกณฑ์

| ถ้า ICC จริงเท่ากับ | ต้องใช้กี่คู่ |
|---|---|
| 0.95 | 9 |
| 0.92 | 14 |
| 0.90 | 19 |
| 0.88 | 27 |
| 0.85 | 51 |
| 0.82 | 117 |
| 0.80 | 247 |

> **แก้ไข 2026-10-01: ตารางนี้คำนวณจากช่วงความเชื่อมั่นแบบ Fisher-z ซึ่ง `icc.js` เลิกใช้แล้ว**
> ตอนนี้ใช้ช่วงแบบ F ของ McGraw & Wong (สูตรเดียวกับ `irr` ใน R และ pingouin) ตัวเลขต่างกันเพียง 1–2 คู่
> (0.95→7, 0.92→12, 0.90→17, 0.88→26, 0.85→50, 0.82→116, 0.80→245)
> สิ่งที่ต้องแก้มากกว่าคือ "ความหมาย" ของตาราง: แต่ละแถวคือจำนวนคู่ที่ช่วงซึ่งมีจุดกึ่งกลางอยู่ที่ค่าจริงพอดีผ่าน 0.75
> นั่นเท่ากับโอกาสผ่านประมาณ **ครึ่งต่อครึ่ง** ไม่ใช่ power
> จากการจำลองที่ power 80% (ไม่มี rater bias, 600 รอบ): 0.95 → ~14, 0.92 → ~26, **0.90 → ~36, 0.88 → ~60**, 0.85 → ~110
> ถ้ามี rater bias ต้องใช้มากกว่านี้ ให้วางแผนขนาด cohort จากตัวเลข 80%

ตารางนี้คือการคำนวณกำลังทดสอบล่วงหน้าของการศึกษา และเผยแพร่ก่อนการรันยืนยันผล
เมื่อมี fixture อยู่ 26 ชุด จึงพิสูจน์ได้เฉพาะความสอดคล้องจริงที่ราว 0.9 ขึ้นไปเท่านั้น
ข้อนี้ถูกระบุและยอมรับไว้ล่วงหน้า ไม่ใช่ค้นพบภายหลัง

**อัตราส่วน** — ใช้ Wilson interval สำหรับสัดส่วน และ Fisher's exact test สำหรับการเทียบก่อน–หลัง
ของจำนวนครั้งที่ parse ไม่ผ่าน ทุกอัตราส่วนในเอกสารนี้แสดงเป็นจำนวนนับกำกับไว้ด้วย
เพราะที่ตัวหารระดับนี้ ค่าร้อยละปิดบังว่าหลักฐานบางเพียงใด

**การแยกส่วนความแปรปรวน** — สำหรับแต่ละการรันแบบจับคู่ mean squares ที่อยู่เบื้องหลัง ICC
ถูกรายงานเป็นส่วนเบี่ยงเบนมาตรฐานสองค่าบนสเกล composite:

- `sdBetween` = √(max(0, (MS_between − MS_error) / k)) — **episode** ต่างกันเองมากแค่ไหน
- `sdError` = √(MS_error) — **ผู้ให้คะแนนสองราย** ต่างกันบน episode เดียวกันมากแค่ไหน

อัตราส่วนของสองค่านี้ใช้วินิจฉัยได้ เพราะ ICC คืออัตราส่วนความแปรปรวน อัตราส่วนที่ต่ำกว่า 1
จึงกดเพดานของสัมประสิทธิ์ไว้ต่ำกว่า 0.5 ไม่ว่าโมเดลจะทำได้ดีเพียงใด `methodology-figures.mjs`
ตรวจสอบตัวเองว่าองค์ประกอบเหล่านี้ให้ค่า ICC ของ production กลับมาได้ตรงถึงทศนิยมสามตำแหน่ง

**Permutation test** — เพื่อตอบว่า held-out แคบผิดปกติหรือแค่เล็ก จึงแจงนับ subset ทั้งหมด
C(26, 8) = 1,562,275 ชุด แล้วรายงานสัดส่วนที่มีส่วนเบี่ยงเบนมาตรฐานไม่เกินค่าที่สังเกตได้
วิธีนี้แม่นยำและไม่ต้องใช้ seed ส่วน Monte Carlo แบบ seeded 20,000 ครั้งคำนวณไว้ด้วยและให้ผลตรงกัน
เพื่อตรวจทานการแจงนับเท่านั้น

**ไม่มีการปรับค่า multiplicity และไม่มีการอนุมานรายมิติ** — ICC รายมิติทั้งเจ็ดรายงานไว้เพื่อบรรยายเท่านั้น
ที่ขนาดตัวอย่างระดับนี้มันไม่ใช่ข้อค้นพบ หัวข้อ 7.7 แสดงว่ามิติหนึ่งอ่านได้ 0.055, 0.663 และ 0.294
ในสามการรันของ configuration เดียวกัน

## 7. ข้อจำกัดด้านความตรง (Threats to validity)

เรียงตามระดับที่จำกัดข้อสรุป หลายข้อค้นพบจากการที่พบว่าตัวเลขที่เผยแพร่ไปแล้วผิด และบันทึกไว้ในรูปนั้น
เพราะรูปแบบความผิดพลาดคือส่วนที่นำไปใช้ต่อได้

### 7.1 การจำกัดพิสัย (range restriction) ใน split ยืนยันผล

แสดงไว้ในหัวข้อ 6.3 และ 6.4 ผลต่อการตีความคือ **การศึกษานี้แยกไม่ออกระหว่าง "โมเดลทดสอบไม่สอดคล้องมากขึ้น
บน held-out" กับ "episode ของ held-out จำแนกได้น้อยกว่า"** และตัวชี้วัดประกอบทั้งหมดชี้ไปทางข้อหลัง
ช่วงความเชื่อมั่น 0.000 – 0.873 ไม่ตัดทั้งความสอดคล้องที่ดีและที่แย่ออกไป

นี่คือรูปแบบความล้มเหลวเดียวกับที่วัดได้กับผู้ตรวจที่เป็นมนุษย์ ซึ่งเกณฑ์ของระบบต้องพึ่งพาในที่สุด:
ที่ baseline ความสอดคล้องของมนุษย์ ICC = **−0.315** ที่ n = 5 โดยมี SD ระหว่าง episode 2.44
เทียบกับ SD ความคลาดเคลื่อน 2.69 — episode ห้าชุดที่มนุษย์ให้ 74–80 และ AI ให้ 71–91
ต่างกันเองไม่มากพอให้ผู้ให้คะแนนรายใดถูกแสดงว่าเห็นตรงกันได้
**การจำกัดพิสัยคือข้อค้นพบที่เกิดซ้ำของโครงการนี้ และเป็นคุณสมบัติของชุดข้อมูล ไม่ใช่ของโมเดลใด**

### 7.2 reference standard เองก็ไม่นิ่ง และแทบไม่มีใครวัดข้อนี้

การศึกษาความสอดคล้องรับความน่าเชื่อถือของ reference มาเต็ม ๆ ของเราวัดแล้ว และไม่ดี
เมื่อให้คะแนน episode เดิม (PLE-045) ซ้ำที่ temperature 0:

| | composite ในแต่ละครั้ง | พิสัย | ครั้งที่ผิด schema |
|---|---|---|---|
| โมเดลทดสอบ | 16, 16, 16, 16, 17 | **1** | 0 จาก 5 |
| **โมเดลเดิม** | 12, 16, 21, 13 | **11** | 2 จาก 6 |

บน episode นั้น โมเดลคลาวด์ระดับแนวหน้าเป็นฝ่ายที่คงเส้นคงวา*น้อยกว่า* บนสเกล 0–35
ที่ช่องว่างระหว่างสองโมเดลทั้งหมดอยู่ราว 4 คะแนน เมื่อดูทั้งชุดข้อมูล ราว **59%**
ของความแปรปรวนระหว่างการรันของโมเดลทดสอบเป็น level shift ร่วมทั้งชุด ไม่ใช่ noise รายมิติ
และชุด fixture ที่ล้มเหลวของสองโมเดลแทบไม่ทับกัน

ข้อนี้เป็น n = 1 episode สำหรับโมเดลเดิม จึงต้องไม่ตีความเกินตัว แต่เพียงพอที่จะยืนยันว่า
reference standard มีความคลาดเคลื่อนของการวัดที่ไม่เล็ก ซึ่งกดเพดานของสัมประสิทธิ์ความสอดคล้องใด ๆ
เท่าที่ทราบ งาน LLM-as-judge ส่วนใหญ่รายงานความสอดคล้องกับโมเดลแนวหน้าโดยไม่เคยวัดโมเดลนั้นกับตัวเอง
**เมื่อ reference เป็นโมเดล ควรรายงาน test–retest reliability ของมันคู่กับค่าความสอดคล้องเสมอ**
มิฉะนั้นค่าความสอดคล้องจะไม่มีสเกลให้ตีความ

### 7.3 ไม่มีตัวเลขความสอดคล้องใดในโครงการนี้ที่เคยเกี่ยวข้องกับผู้ให้คะแนนที่เป็นมนุษย์

ค่า ICC 0.811 ของ evaluator ที่มักถูกอ้าง วัดกับ agent-rater **จำลอง** 3 ตัวที่กำหนดจุดยืนไว้
บน cohort ที่สร้างขึ้นใหม่หลังชุดเดิมถูกลบโดยขั้นตอนล้างข้อมูลของตัวเอง และ prompt ที่ให้ค่า 0.811
ก็ไม่ได้ใช้งานแล้วตั้งแต่ commit ที่ทำให้สอดคล้องกับ CREC082 เข้ามาแทน (หัวข้อ 2.5)
ผลคือการศึกษานี้เทียบโมเดลที่ทดสอบกับโมเดลเดิมที่ไม่ทราบความสอดคล้องกับผู้เชี่ยวชาญ
โดยใช้ prompt ที่ยังไม่เคยวัดความสอดคล้องกับสิ่งใดเลย gate ชั้นตัดสิน — โมเดลเทียบกับมนุษย์ —
จึงยังเป็น go/no-go ที่แท้จริงของโครงการ และไม่ได้รับผลกระทบจากสิ่งใดในรายงานฉบับนี้

### 7.4 Survivorship bias: ตัวชี้วัดดีขึ้นเมื่อโครงสร้างพื้นฐานแย่ลง

เมื่อการรันสูญเสีย fixture จากความล้มเหลวของการเชื่อมต่อ สิ่งที่หายไปไม่ได้สุ่ม
transcript ที่ยาวกว่าใช้เวลาให้คะแนนนานกว่า จึงเป็นทั้งชุดที่เครื่องไม่เสถียรทำหลุด **และ**
ชุดที่สองโมเดลเห็นไม่ตรงกัน ในทุกการรันที่มีการสูญเสีย ค่าเฉลี่ย Σ|Δ| ของ fixture ที่หายไป
สูงกว่าของชุดที่รอด:

| การรัน | หายไป | ค่าเฉลี่ย Σ\|Δ\| ของที่หาย | ของที่รอด | ผลต่าง |
|---|---|---|---|---|
| #6 addendum | 4 | 4.19 | 3.07 | +1.12 |
| #9 c5ffe rep2 | 6 | 4.64 | 3.25 | +1.39 |
| #7 median3 | 3 | 5.44 | 3.33 | +2.11 |
| #2 v0 | 2 | 4.50 | 4.13 | +0.38 |

สี่จากสี่ไปในทิศทางเดียวกัน โดยมีกลไกที่ทำนายทิศทางได้ล่วงหน้า หลักฐานที่ชัดที่สุดคือการรัน #8 กับ #9:
โมเดล prompt กฎ และเครื่องเดียวกัน ห่างกัน 112 นาที ได้ **0.611 เมื่อครบ 18 fixture เทียบกับ 0.795
เมื่อเหลือ 12** การรันที่สูญเสียหนึ่งในสามของตัวอย่าง ได้คะแนนสูงกว่า 0.18

บรรเทาแล้วตั้งแต่ commit `9ea5636` ด้วยการ retry ความล้มเหลวของการเชื่อมต่อ (สูงสุด 4 ครั้ง
backoff เพิ่มเท่าตัวจาก 20 วินาที) และการแยกความล้มเหลวของการเชื่อมต่อออกจากความล้มเหลวของโมเดล
ณ จุดที่เรียก **ตัวเลขทุกตัวที่บันทึกก่อน commit นั้นมี bias ติดอยู่** การรันยืนยันผลไม่สูญเสียอะไรเลย

ข้อสรุปที่นำไปใช้ทั่วไปได้: harness ที่ทิ้งเคสยากไปเงียบ ๆ จะรายงานโมเดลที่ดีกว่าความจริง
ต้อง retry การสูญเสีย และต้องรายงานอัตราการสูญเสียคู่กับตัวชี้วัดเสมอ

### 7.5 คันโยกที่ตั้งค่าไว้ บันทึกไว้ และไม่เคยทำงาน

การรัน #7 มี `consistency: "median3"` ประทับอยู่ใน report แต่มันรัน `adaptive`
probe ส่งค่า flag ต่อไปยัง report ในขณะที่จุดเรียกใช้ตั้งโหมดตายตัวไว้ ทุกแถวจึงแสดงการเรียกสองครั้ง
ทั้งที่ `median3` จริงต้องเรียกสามครั้ง configuration ที่ "ต่างกัน" ของ #6 กับ #7 จึงเป็น configuration
เดียวกัน และผลต่าง 0.735 → 0.762 คือผลต่างของการรันซ้ำที่ n = 14/15 ไม่ใช่ผลของตัวแปรที่ทดลอง
**`median3` จึงยังไม่เคยถูกวัดเลย**

กฎที่นำไปใช้ต่อได้: **ตรวจสอบจากหลักฐานการทำงานจริง ไม่ใช่จาก configuration**
จำนวนการเรียก จำนวน token และเวลาตอบ ต่างบันทึกความจริงไว้ครบ มีเพียง flag ที่โกหก
configuration ที่ประทับไว้เป็นบันทึกของ*เจตนา*

### 7.6 Parseability: กฎการนับที่คำนวณผิดสี่แบบในวันเดียว

เกณฑ์ JSON ถูกต้อง ≥98% ให้คำตอบสี่แบบเกี่ยวกับการรันชุดเดียวกันก่อนจะลงตัว: 95.4%
(คิดความล้มเหลวของการเชื่อมต่อและของฝั่งคลาวด์เป็นความผิดของโมเดลทดสอบ) แล้วเป็น "100%"
(ตัด `Pis7ScoreError` ออก ซึ่งคือการผิดสัญญาที่เกณฑ์นี้มีไว้จับพอดี — การตัดนี้ปิดสวิตช์เกณฑ์ทิ้ง
เปลี่ยนการรันที่ 5 จาก 18 แถวล้มเหลวให้กลายเป็นผ่านสะอาด) แล้วจึงเป็น 94.4% นับต่อการเรียก

ความกำกวมต้นทางเป็นเรื่องจริงและควรระบุชื่อไว้: HTTP client ไม่เคย throw
timeout จึงคืน body ว่าง สตริงว่าง parse ได้เป็น `{}` schema ล้มเหลว และเครื่องที่ตายกับคำตอบขยะ
แยกจากกันไม่ออก ณ จุดที่จัดประเภทข้อผิดพลาด แก้ได้ที่จุดเรียกเท่านั้น ที่ซึ่งสถานะการเชื่อมต่อยังมองเห็นอยู่
จึงเกิดกฎสองข้อที่ตอนนี้มี unit test แล้ว (`scripts/probe/parseability.mjs`, 13 เคส):
**มีเพียงความล้มเหลวของการเชื่อมต่อเท่านั้นที่ออกจากตัวหาร** และ **นับการเรียก ไม่ใช่นับ fixture**

แยกอีกประเด็น: เกณฑ์นี้ตัดสินไม่ได้ที่ขนาดตัวอย่างระดับนี้ การถดถอยที่ดูเหมือนเกิดจาก addendum
97.4% → 94.4% คือ parse ผิด 1 ใน 38 เทียบกับ 2 ใน 36 — Fisher exact **p = 0.61** และ p = 1.00
หลังจัดประเภทหนึ่งรายการใหม่เป็น timeout ด้วยหลักฐานจำนวน token ที่เป็น deterministic
ทุกช่วงความเชื่อมั่นคร่อม 98% รวมทั้งของ baseline เอง การจะผ่าน 98% ด้วยความเชื่อมั่น 95%
ต้องมีการเรียกที่สะอาดติดต่อกัน **189 ครั้ง** อย่างไรก็ตามกลไกที่แท้จริงถูกค้นพบและแก้ไปแล้วตามเนื้อผ้า:
กฎ symmetric evidence ใน addendum ทำให้อัตราที่โมเดลยกข้อความจาก transcript มาใส่ในสตริง JSON
เพิ่มจากราว 3% ของคะแนนรายมิติเป็นราว 55% และตัวอย่างใน addendum เองก็ใช้เครื่องหมาย double quote
ที่ทำให้ parser พัง การเปลี่ยนเป็น single quote ทำให้ hash ของ prompt เปลี่ยน
ซึ่งทำให้การวัดที่ทำด้วย prompt ก่อนหน้าใช้ไม่ได้

**ความผิดพลาดของการวัดที่เข้าข้างโมเดล ไม่สมมาตรกับความผิดพลาดที่ใส่ร้ายโมเดล** —
แบบหลังจะถูกจับได้ในการรันถัดไป แบบแรกจะหลุดออกไปถึงผู้อ่าน

### 7.7 สัมประสิทธิ์รายมิติที่ n ระดับนี้ไม่ใช่ข้อค้นพบ

ในสามการรันของ configuration เดียวกัน d1 อ่านได้ **0.055 → 0.663 → 0.294**
เรื่องเล่าที่สร้างจากการรันที่ 2 ("addendum ช่วย d1 โดยแลกกับ d6") ถูกหักล้างในการรันที่ 3
ซึ่ง d6 ฟื้นเป็น 0.745 และ d1 ทรุด ICC รายมิติเจ็ดค่าที่ n ≈ 15 โดยไม่ปรับ multiplicity
ย่อมให้รูปแบบที่ดูเหมือนมีความหมายเสมอ

สัญญาณเดียวที่นิ่งในทุกการรันคือ **d4 การสืบค้นแบบต่อยอด** ซึ่งต่ำที่สุดทุกครั้ง
(0.425 / 0.552 / 0.530) และเป็นชนิดที่การ calibrate แก้ไม่ได้: ค่า*เฉลี่ย* d4 ของสองโมเดล
ต่างกันเพียง 0.07 แต่การจัดอันดับราย episode ไม่ตรงกัน หากจะทำงาน prompt ต่อ นั่นคือจุดที่มีที่ว่างให้ปรับ
แม้กระนั้นข้อนี้ก็เสนอไว้เป็นสมมติฐานสำหรับการศึกษาที่มีกำลังทดสอบเพียงพอ ไม่ใช่ผลการศึกษา

### 7.8 ความแปรปรวนระหว่างการรันที่ configuration คงที่

การสุ่มสองครั้งจาก configuration เดียวกันห่างกันราวเก้าสิบนาทีให้ 0.611 กับ 0.795 (หัวข้อ 7.4)
และอีกคู่หนึ่งให้ 0.735 กับ 0.762 (หัวข้อ 7.5) ที่ n ≈ 15 sampling noise ของสถิตินี้
อยู่ในระดับเดียวกับทุกผลที่การศึกษาตั้งใจจะตรวจจับ การสุ่มสองครั้งจาก configuration เดียวกัน
คือค่าประมาณ noise ที่ดีที่สุดเท่าที่มี และควรรายงานเช่นนั้น ไม่ใช่รายงานเป็นผลของตัวแปรที่ทดลอง

### 7.9 ฮาร์ดแวร์ที่ใช้ร่วมกันและควบคุมไม่ได้

โมเดลที่ทดสอบรันบนเครื่องที่บุคคลที่สามดูแล ให้บริการโมเดลอื่นอีกหลายตัวแก่ผู้ใช้รายอื่น
เข้าถึงผ่าน VPN และผ่าน gateway ไม่ใช่การเชื่อมตรง งานเดียวกันใช้เวลา **57 วินาที กับ 956 วินาที
ห่างกันสองชั่วโมง** ครั้งหนึ่ง prompt ขนาด 30 token ตอบใน 1 วินาที ขณะที่ transcript ที่สั้นที่สุดของ tuning
ใช้เวลาเกิน 10 นาที ไม่มีค่า timeout หรือ concurrency ใดป้องกันงานของเพื่อนบ้านได้
การรัน probe สองงานพร้อมกันเคยทำให้เครื่องแย่ลงหลายชั่วโมง หลังจากนั้นจึงกำหนดกฎว่ารันครั้งละหนึ่งงาน

ข้อนี้กระทบตัวเลขเวลาตอบโดยตรง และกระทบตัวเลขความสอดคล้องโดยอ้อมผ่านหัวข้อ 7.4
และเป็นเหตุผลที่ตรึงเวอร์ชันโมเดลไม่ได้ (หัวข้อ 2.4): เครื่องที่ผู้อื่นเปลี่ยน weight ได้
ย่อมรองรับ Model Lock record ไม่ได้

### 7.10 ความ optimistic จาก tuning สู่การยืนยันผล ซึ่งปนกับข้อ 7.1

ค่าประมาณบน tuning split ด้วย prompt สุดท้ายคือ 0.611 และ 0.795 ส่วนค่าประมาณจากการยืนยันผลคือ 0.436
ส่วนหนึ่งของการลดลงนี้คือความ optimistic ตามปกติของค่าประมาณที่วัดบนข้อมูลที่ใช้พัฒนา —
ซึ่งคือสิ่งที่ held-out split มีไว้เปิดโปงพอดี และมันทำงาน แต่แยกออกจากการจำกัดพิสัยในข้อ 7.1
ไม่ได้อย่างสะอาด เพราะ episode แปดชุดเดียวกันแบกทั้งสองผลไว้ ชุดข้อมูลที่ใหญ่กว่า
และแบ่งให้ทั้งสองฝั่งครอบคลุมพิสัยทั้งสเกล จะแยกได้ ชุดนี้แยกไม่ได้

### 7.11 เส้นทางที่วัด ไม่ใช่เส้นทางที่จะให้บริการจริง

ตัวเลขทุกตัวในรายงานนี้ผลิตโดย `scripts/probe/*` ซึ่งเป็นชุดเครื่องมือที่เรียกโมเดลโดยตรง มันใช้
*เครื่องมือวัด* ชุดเดียวกับ service ที่ให้บริการจริง — น้ำหนักเกณฑ์เดียวกัน prompt ที่ประกอบแบบเดียวกัน
โมดูล self-consistency ตัวเดียวกัน ทั้งหมด import จาก `rimpl/src/lib` และ `rimpl/src/services` — แต่ไม่ใช่
*เส้นทางส่งข้อมูล* เดียวกัน ตัว provider adapter คิวที่จำกัดจำนวน ตัวถอดข้อมูลระบุตัวตน และตัวสร้าง

## 8. ข้อสรุป และสิ่งที่การศึกษาในอนาคตต้องมี

### 8.1 สิ่งที่การศึกษานี้ยืนยันได้

1. **screening gate ให้ผล `insufficient`** — ICC(A,1) = 0.436 (0.000 – 0.873) บน held-out split
   ที่กันไว้ ช่วงความเชื่อมั่นคร่อมเกณฑ์ 0.75 ที่ค่าประมาณจุดนี้ ไม่มีจำนวนคู่เพิ่มเติมเท่าใด
   ที่จะทำให้ขอบล่างเกิน 0.75 ได้
2. **การรันเพิ่มบนชุดข้อมูลนี้เปลี่ยนผลไม่ได้** และเหตุผลวัดได้ ไม่ใช่การคาดเดา:
   ความแปรปรวนระหว่าง episode ของชุดยืนยันผล น้อยกว่าความแปรปรวนของความคลาดเคลื่อนของผู้ให้คะแนน
3. **ความสอดคล้องเชิงสัมบูรณ์ของโมเดลที่ทดสอบอยู่ในเกณฑ์ดี และรักษาสัญญารูปแบบผลลัพธ์ได้สะอาด** —
   sdError 7.02, Σ|Δ| มัธยฐาน 2, JSON ถูกต้อง 16 จาก 16 การเรียก, ไม่สูญเสีย fixture เลย —
   ซึ่ง**ไม่ใช่**สิ่งเดียวกับการผ่านเกณฑ์ และต้องไม่รายงานราวกับว่าใช่
4. ในทางปฏิบัติ: โมเดลเดิมยังเป็นผู้ให้คะแนนของการประเมินที่นำไปสู่หน่วยกิต
   ส่วนโมเดลที่ทดสอบใช้เฉพาะงานที่ไม่นำไปสู่หน่วยกิต ซึ่งไม่มี gate ความสอดคล้องบังคับ

### 8.2 สิ่งที่การศึกษานี้ยืนยันไม่ได้

- ไม่ได้ยืนยันว่าโมเดลที่ทดสอบให้คะแนนไม่สอดคล้องกับโมเดลเดิม
- ไม่ได้ยืนยันว่าโมเดลที่ทดสอบเหมาะจะใช้ให้คะแนน — screening gate ยอมรับไม่ได้โดยการออกแบบ
  และ n = 8 ก็ไม่รองรับข้อสรุปเชิงยอมรับใด ๆ อยู่แล้ว
- ไม่ได้บอกอะไรเลยเกี่ยวกับความสอดคล้องกับผู้เชี่ยวชาญที่เป็นมนุษย์ ซึ่งเป็นคำถามที่ตัดสินหน่วยกิตจริง

### 8.3 สิ่งที่การศึกษาในอนาคตต้องมี

1. **episode ที่เลือกให้ครอบคลุมทั้งสเกล** — นี่คือข้อจำกัดที่ผูกมัดอยู่ ชุดข้อมูลที่ composite
   กระจุกตัวย่อมรับรองผู้ให้คะแนนรายใดไม่ได้ และการเพิ่มผู้ให้คะแนนหรือเพิ่มการรันไม่ช่วย
   การสุ่มควรแบ่งชั้นตามพิสัยของ composite ซึ่งต้องให้คะแนนกลุ่มตัวอย่างที่ใหญ่กว่านี้ก่อนแล้วจึงคัดเลือก
2. **reference standard ที่เผยแพร่ test–retest reliability ไว้** — ถ้า reference เป็นโมเดล
   ให้รันกับตัวเองแล้วรายงานตัวเลขนั้นคู่กับค่าความสอดคล้อง ถ้าเป็นมนุษย์
   ให้รายงาน inter-rater reliability บน episode ชุดเดียวกัน
3. **คำนวณกำลังทดสอบก่อนเก็บข้อมูล** — ตารางจำนวนคู่ในหัวข้อ 5 คำนวณง่ายมาก
   และจะบอกเราตั้งแต่วันแรกว่า fixture 26 ชุดพิสูจน์ได้เฉพาะความสอดคล้องที่ราว 0.9 ขึ้นไป
4. **harness ที่ retry และรายงานการสูญเสียของตัวเอง** — ดูหัวข้อ 7.4
5. **โมเดลที่ตรึงเวอร์ชันได้** — base release, checksum ของ weight, เวอร์ชัน engine และ quantization
   บนฮาร์ดแวร์ที่อยู่ภายใต้การควบคุมการเปลี่ยนแปลง ไม่มีข้อใดได้มาในการศึกษานี้
6. **ชุดยืนยันผลที่ใหญ่กว่าที่สัญชาตญาณบอก** หรือแบ่งชั้นตามผลลัพธ์
   ตัวอย่างยืนยันผล 8 ชุดที่สุ่มจาก 26 มีโอกาส 6.47% ที่จะไม่ให้ข้อมูลอย่างน้อยเท่าที่เราสุ่มได้
   ซึ่งไม่ใช่ความเสี่ยงที่ห่างไกล

## 9. การทำซ้ำ (Reproducibility)

### 9.1 ข้อมูลและโค้ด

| สิ่งประดิษฐ์ | ที่อยู่ | commit ไว้หรือไม่ |
|---|---|---|
| report ของการรัน (JSON 10 ไฟล์) | `scripts/probe/report/*.json` | ใช่ |
| ผลตัดสินของ held-out | `scripts/probe/report/heldout-c5ffe-adaptive.verdict.json` | ใช่ |
| manifest ของ split + SHA-256 รายไฟล์ | `scripts/probe/SPLIT.json` | ใช่ |
| สคริปต์สร้างตัวเลขซ้ำ | `scripts/probe/report/methodology-figures.mjs` | ใช่ |
| transcript | `scripts/probe/fixtures/*.json` | **ไม่** — เป็นบทสนทนาทางคลินิก |

report มีเฉพาะคะแนนและตัวระบุ: ในทั้งสิบไฟล์มีค่าสตริงที่ไม่ซ้ำกันรวม 60 ค่า — timestamp, git SHA,
รหัสนามแฝง `PLE-NNN`, ชื่อโหมดและชื่อโมเดล, hash ของ prompt และป้ายกำกับของ probe
ไม่มีข้อความเหตุผล ไม่มี transcript ไม่มีการอ้างอิงถึงผู้ป่วย

### 9.2 คำสั่ง

```sh
# 2  agreement พื้นฐาน ไม่มี addendum
node scripts/probe/model-agreement.mjs --split tuning --consistency adaptive \
     --out scripts/probe/report/tuning-agreement-v0.json
# 3-5  noise floor ปิดแล้วเปิด addendum
node scripts/probe/repeat-consistency.mjs --arm local --split tuning --fixtures 18 --repeats 5 \
     --addendum off --out scripts/probe/report/noise-2026-09-03-noaddendum.json
# 6-9  agreement กับ addendum แต่ละเวอร์ชัน
node scripts/probe/model-agreement.mjs --split tuning --consistency adaptive \
     --out scripts/probe/report/tuning-agreement-c5ffe-adaptive.json
# 11   ตรวจก่อนเปิด split
sh scripts/probe/canary.sh
# 12   การรันยืนยันผล — ครั้งเดียวเท่านั้น
node scripts/probe/model-agreement.mjs --split heldout --consistency adaptive \
     --attempts 4 --retry-base-ms 20000 \
     --out scripts/probe/report/heldout-c5ffe-adaptive.json
```

เครื่องมือตัดสินเรียกใช้ implementation ของ ICC ที่ใช้ใน production จึงต้องรันจาก `backend/`:

```sh
cd backend && node ../scripts/probe/screening-verdict.mjs \
  --agreement ../scripts/probe/report/heldout-c5ffe-adaptive.json --json
```

exit code: 0 ผ่าน · 1 ไม่ผ่าน · 3 ข้อมูลไม่พอ · 2 ตั้งค่าผิด · report ของ tuning split ต้องใช้
`--allow-tuning` และจะถูกกำกับว่า "not a gate result" ในผลลัพธ์

### 9.3 การตรวจสอบที่มาซึ่งทำงานอัตโนมัติ

- SHA-256 ของทุก fixture ถูกตรวจซ้ำกับ manifest ของ split ในทุกการรัน
- ทุก report บันทึกเวอร์ชัน prompt ของทั้งสองฝั่งไว้ครบ และเครื่องมือตัดสินจะเทียบเวอร์ชันที่บันทึกไว้
  กับ working tree แล้วเตือนเมื่อ report อธิบาย prompt ที่ไม่มีอยู่แล้ว
- สคริปต์สร้างตัวเลขตรวจสอบตัวเองว่าองค์ประกอบความแปรปรวนให้ค่า ICC ของ production กลับมาได้ตรง
  ถึงทศนิยมสามตำแหน่ง และตรวจการแจงนับ permutation แบบสมบูรณ์เทียบกับ Monte Carlo แบบ seeded

## 10. หมายเหตุเรื่องขอบเขตและถ้อยคำ

ข้อความสามข้อที่ปรากฏในเอกสารโครงการข้างเคียง **ต้องไม่** ถูกนำไปใส่ในบทความ:

1. **ยังไม่ได้ทำ provider randomisation** — สถาปัตยกรรมระบุการสุ่มผู้ให้บริการ AI ราย session ไว้
   แต่ `docs/constraints.md:4` กำกับว่า *"Planned — not yet implemented; runs Claude-only."*
   จึงเขียนประโยคใดเกี่ยวกับการสุ่มผู้ให้บริการในลักษณะ as-built ไม่ได้
2. **"PII ไม่เคยออกนอกประเทศไทย" เป็นเท็จ** — ฐานข้อมูลของแอปพลิเคชันตั้งอยู่ที่ `ap-northeast-1`
   ข้อกล่าวอ้างที่ปกป้องได้แคบกว่านั้นและยังคุ้มค่าที่จะกล่าว: การประมวลผลบนเครื่องภายในองค์กร
   ตัด hop ของการ inference บนคลาวด์ออกไป การ de-identify จึงกลายเป็นการป้องกันเชิงลึก
   แทนที่จะเป็นด่านเดียว
3. **ศัพท์** — ใช้ *PLE* (Professional Learning Episode) ตลอด · **Pilot Study**
   (แพทย์ 75 คน × 3 episode) **ยังไม่เริ่ม** · กิจกรรมช่วงสิงหาคม–กันยายน 2569 คือรอบ sandbox
   ซึ่ง session ถูกกำกับว่าเป็นการทดสอบและไม่นับรวมในสิ่งใด

**จริยธรรมการวิจัย** — transcript ทุกชุดผ่านการ de-identify ด้วย filter ของ production ก่อนที่โมเดลใด
จะได้เห็น ภายใต้โครงการ CREC082 ไม่มีข้อมูลผู้เข้าร่วมปรากฏในเอกสารนี้หรือในสิ่งประดิษฐ์ใดที่ commit ไว้

**สถานะ** — เอกสารนี้รายงานผล screening ไม่ใช่การรับรองว่าโมเดลใดใช้ให้คะแนนการให้เหตุผลทางคลินิก
ของแพทย์ได้ และไม่มีการตัดสินหน่วยกิตใดตั้งอยู่บนเอกสารนี้
