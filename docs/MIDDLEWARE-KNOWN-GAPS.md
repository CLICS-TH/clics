# RIMPL Middleware — Known Gaps vs. the Architecture Flowchart

_The middleware **works end-to-end as a Claude-only pipeline** (PII masking → anti-sycophancy / citation / Socratic system prompt → Claude → post-checks). The items below are places where the current implementation is **narrower than the printed 4-layer flowchart**. They are documented intentionally._

> **Two framings in that sentence are out of date.** The "July–September 2026 pilot build" schedule is
> superseded — neither milestone started ([pilot-timeline.md](pilot-timeline.md)). And "the pilot
> decision is to run Claude-only" is now contradicted by the local-model programme: D8 moves every
> purpose on-premise and the CREC submission set forecloses a commercial external API for research
> transcripts ([LOCAL-MODEL-ROADMAP.md](LOCAL-MODEL-ROADMAP.md) D8/D17). Claude-only is what runs
> **today**, not the decision of record — which makes L4 below a gap to retire rather than to build._

## L4 — API Randomization Layer (multi-provider) — NOT IMPLEMENTED
- The flowchart shows L4 randomizing the AI provider per session across **Claude / GPT-4o / Gemini / Mistral** via `hashSessionId()`, with failover and `provider_used` logging.
- Reality: `rimpl/src/services/claude.js` hard-codes a single model (`claude-sonnet-4-6`) and is the only provider client. There is **no `hashSessionId()`, no GPT-4o/Gemini/Mistral client, no failover, and no per-session provider selection.**
- `ples.provider_used` exists in `db/schema.sql` but is a static default (`'claude'`), not a logged runtime choice.
- **Impact:** the privacy/bias rationale of vendor rotation is not exercised. All de-identified traffic goes to Claude.

## PII de-identification — BROADENED (2026-06-09); residual free-text-name risk
- `rimpl/src/services/pii-filter.js` is now a **multi-category de-identifier**: NAME (Thai/English title-led, labelled `ชื่อ…นามสกุล…` and the English `Name` / `Patient name` / `Surname` / `Family name` / `Last name`, nicknames, plus bare re-occurrences of already-seen names), EMAIL, LINE id, Thai national ID, HN (also `Hospital number`), MRN/AN/`ID`, PHONE (Thai + international), DATE, WARD, ADDR (house no. / หมู่ / ตำบล-อำเภอ-จังหวัด, and the English `Subdistrict` / `District` / `Province` / `Village` / `Address`). The English labels (#422, for the booth's English look) mask the words after them up to the first prose word; a bare lowercase `name` or `address` with no colon or `is` after it is read as the verb ("name the cause", "address hypoxia first"), so `name john smith` typed that way still goes out as typed — with **stable per-category indexed tokens** (`[NAME-1]`, `[HN-1]`, …) so repeated mentions collapse to one referent.
- It is complemented by a **structured patient-identifier intake**: `ple_patient_refs` (`db/migration-patient-intake.sql`) holds the patient identifier in a physically separate, **owner-only** table (deny-all RLS + route-layer physician filter) that is **never** read by the cloud-AI payload, the auditor blind queue, or the export — keeping the case narrative name-free by construction; the filter remains the backstop for anything typed into the narrative.
- The flowchart's **stable pseudonymization** is **partially built now**: `professionals.pseudonym` (P-NNN) is assigned at account creation/approval, and OAuth real identities are AES-256-GCM-encrypted in the deny-all `oauth_identities` vault (see [constraints.md](constraints.md)). The **PLE-001…PLE-150** session pseudonyms (Phase 2) and the **reversible on-prem token→value map** (`ple_pii_map`, 2026-06-18 — see below) now exist; in-message masks are recoverable for Tier-1 audit while staying de-identified everywhere else.
- **Bare-name leak — CLOSED (2026-06-18):** the once-residual unlabelled name (`สมชายมาด้วยไข้`) is now masked by two added layers: (1) an **intake-hint pass** — the backend forwards the physician's structured `patient_ref` (on-prem) to RIMPL on the chat + evaluate calls so those exact strings are scrubbed verbatim, even mid-sentence (`deriveHintTokens` in `pii-filter.js`); and (2) a conservative **Thai given-name gazetteer** backstop (`rimpl/src/services/pii-names.th.js`) that masks a common bare name at a boundary + clinical-lead/standalone, when no intake was entered. Both feed the existing `[NAME-n]` registry. **(3) a Chinese-Thai clan-surname pass (2026-06-22, `TH_SURNAMES` in `pii-names.th.js`)** masks `แซ่X` surnames VERBATIM in any position — the `แซ่` prefix is an unambiguous surname marker, so it closes the bare-surname-after-given-name leak (incl. the glued form `แซ่ลี้เข้ารับ…`) with no over-masking risk. NATIVE Thai surnames are deliberately NOT hand-seeded (they double as given/place/clinic/pharmacy names → would over-mask clinical text fed to PIS-7). **(4) a bare-surname pass (#224 / #238, PR #232, `applyGivenSurnamePass` in `pii-filter.js`)** takes the word next to any masked Thai given name for the surname and folds it into the same `[NAME-n]`, with no surname list. Owner ruling 2026-10-29, "Mask any word after a name": the word is kept only when ALL of it splits into words of a short, hand-reviewed **clinical continuation allowlist** (`TH_CLINICAL_CONTINUATIONS` in `rimpl/src/services/pii-clinical-words.th.js`, plus the hand lists in `pii-filter.js`; never a surname component in `TH_SURNAME_MORPHEMES`, a gazetteer given name, or `มาก`; a split into several words must hold one of 3+ letters). So a surname that is also an everyday phrase (`ปลอดภัย`, `แข็งแรง`, `ถาวร`) is masked, and so is a clinical statement off the list (`นายสมชาย แข็งแรงดี` → `[NAME-1] [NAME-1]`, accepted). It covers the surname after OR before the given name (`ใจดี นายสมชาย`, up to 20 letters), any separator including a line break (owner ruling, "Yes, cross the line"), comma, parenthesis, hyphen, slash, colon and quotes; invisible format characters such as zero-width space and soft hyphen are stripped from the text AND from the `patient_ref` hints; `ณ อยุธยา`; and a Latin surname in any case (`JAIDEE`, `jaidee`, `na Ayudhya`), unless it is on a short English allowlist (`presented`, `denies`, …) or has a long drug-name ending (`-cillin`, `-azole`). The taken surname, and the shortest head of a glued name word (3+ letters, not on the allowlist, not a lone surname component such as `บุญ`) before an allowlisted tail (`ใจดีครับ` → `ใจดี`; the same for a given name, `นายอรุณครับ` → `อรุณ`), become aliases, folded in later as a whole word or inside a glued run that is not wholly allowlisted (`ญาติของใจดีโทรมา` is masked, `จิตใจดีขึ้น` is not). One surname can expose another (`ใจดี ทองคำ` once `ใจดี` is known), so the pass repeats within a text, and `primeRegistry` runs every text of an outbound call (chief complaint, history, current message; `routes/chat.js`, `deidentify.js`, `audit-discuss.js`, and `stripHistoryPii` for the transcript paths) until a round finds nothing new, before any of them is masked; each round is linear, and past 32 rounds the filter throws, so the route answers 500 (fail closed). `patient_ref` is scrubbed before any cloud call and never forwarded.
- **Booth turns are de-identified in pieces (#406, PR #407):** a booth physician turn is `[vignette \n\n] question \n answer` (`backend/src/services/booth-dialogue.js` `dialogueTurns`). `rimpl/src/routes/chat.js` `deidentifyBoothTurn` masks the vetted vignette on its own and reads the bank question and the visitor's typed answer together, so a label that ends the question still masks the value that opens the answer (#375). The exception is a question that the filter masks on its own: vetted text holds no PII, so that mask is a false positive (a question opening with the pronoun คุณ, `คุณจะส่งตรวจ…`, is read as a name by the คุณ shield, and the surname pass then took the answer on the next line as that name's surname). Such a question is its own text under the one registry, and the answer is read alone. The kept `answer_deidentified` is exactly the answer text the AI saw. The filter itself is unchanged: on every other path, and inside the answer, a surname is still taken across a line break. **Accepted residual (owner ruling on PR #407: "Accept, document fully"):** under a bank question that masks on its own (32 bank variant entries, 21 distinct texts, in 8 of the 11 NFCME-2026 cases, at step 1 in 3 of them; counted 2026-11-09; `booth-typed-answer-survives.test.js` finds them as the questions where `stripPii(q) !== q`), whatever master masked only through that over-mask now goes to the AI as typed, and is kept as typed in `answer_deidentified`. That is: a lone unknown word (`ทองเปลว`, or a Latin word such as `somchai99`); an untitled full name outside the gazetteer, on one line or over two lines (`พรรณราย ทองเปลว`, `พรรณราย\nทองเปลว`); a surname followed by other words (`ทองเปลว ปวดท้อง`); and that word's later mentions in the same play, even under a question that does not mask (`ญาติของทองเปลวโทรมา`), because no alias is registered for it. Before #400 (master 58a39502) the over-mask folded such a word into a phantom name and registered it as an alias, so master masked it there and in its later mentions. Since #400 (master fbbb58ff) the backend sends a typed answer fenced behind a note line (`booth-dialogue.js` `fenced`), so on master the phantom name takes the note's first word (`Typed` → `[NAME-n]`) instead, and the AI gets this whole class as typed on master too (pinned in the same test with master's route: the AI-bound text matches; master stores `answer_deidentified` as null for every fenced typed answer, which this PR fixes by keeping the clean text inside the fence). Under every other bank question, and in scored chat, master sends the same answer in clear and registers no alias, so its later mentions go out too. What this PR adds over current master is the stored copy: `answer_deidentified` now keeps each of these answers as typed, where master keeps null. What still masks everywhere: titled names (`นาย…`, `คุณ…` and the other titles), labelled names (`ชื่อ…`, `นามสกุล…`), gazetteer given names and their adjacent surnames, `patient_ref` hints, HN / MRN, phone, national ID, email and LINE id. The expectations in `booth-typed-answer-survives.test.js` pin each kind, so any change to this class is visible.
- **Reversible on-prem audit map — BUILT (2026-06-18):** at finalization RIMPL returns the de-id `[NAME-n]→raw` registry (on-prem only, never to cloud); the backend AES-256-GCM-encrypts it (`IDENTITY_ENC_KEY`) into `ple_pii_map` — one row per PLE, RLS **deny-all**. Tier-1 (superadmin/PI) re-identifies a token via the gated, **audit-logged** `GET /admin/ples/:id/pii-map` (`action: 'pii.reidentify'`); the export never reads it. Scoped **per-PLE** (no cross-session patient linkage by design).
- **New residual:** a bare name that is (a) NOT recorded in `patient_ref` AND (b) not in the given-name gazetteer / not a `แซ่` clan surname AND (c) not title/label-led AND (d) not next to such a masked given name (a surname there is taken by layer 4 above, with the phrase-surname exception) still leaks (Thai has no word spaces → the gazetteers are best-effort; native surnames are intentionally left to the intake-hint layer rather than hand-seeded, since they collide with given/place/clinic names). The map covers only finalized (tier-1-passed) PLEs.
- **Bare ENGLISH personal name — OPEN (reported 2026-10-02 by the Phase 3 question-bank pass):** an English name with no honorific (`Dr`/`Mr`/`Mrs`/`Ms`/`Miss`/`Prof`), no `nickname` label and not recorded in `patient_ref` passes in clear — `John Smith presented with chest pain` is sent unchanged. There is **no English given-name gazetteer** (the Thai one is Thai-only), and capitalisation alone cannot separate a name from a sentence-initial word, a drug brand or an eponym (Murphy's sign, Parkinson). Mitigation today is the intake-hint pass: a name the physician recorded in `patient_ref` *is* scrubbed verbatim (`tests/pii-false-positives.test.js` proves it). Pinned as a `test.todo` in that file.
- **Clinical false positives — NARROWED (2026-10-02, PR #114):** `คุณ…` (ขอบคุณครับ, คุณหมอ, คุณภาพ), `เชื่อ`/`ชื่อ` + thing-labels (ชื่อยา, ชื่อโรค, ชื่อสามัญ, ชื่อการค้า), English `line` (first-line, joint line, IV line), `ward`/`toward`/`ward round`, and ต่างจังหวัด / รพ.สต. / รพ.จังหวัด were being masked, corrupting the text PIS-7 scores. **How the คุณ / ชื่อ shields work:** the whole glued run after the anchor is split into words from closed lists. It is let through **only if every character is a list word**. Otherwise everything from the last *anchor* (a role / kin word at the head of the run — คุณหมอ, คุณแม่ — or a complete compound such as คุณภาพชีวิต) to the end of the run is masked; with no anchor the whole run is masked, as on master. So a name that begins with a list word (คุณของขวัญ, คุณภาพร, คุณคิดถึง) is masked whole, and คุณแม่ของสมศรี… becomes คุณแม่[NAME-n]. Glued prose the lists do not cover is still over-masked (คุณคิดว่าการวินิจฉัย… → คุณ[NAME-n]; the spaced form survives). **Residual risk, not zero — a name written ENTIRELY of list words passes.** This is a real class, not a theory: สามารถ ("can") and ช่วย ("help") are everyday verbs AND Thai male given names, and while they were list words `คุณสามารถ อายุ 50 ปี` went out with the name in clear (found in the second review of PR #114). Both were removed, as was ประโยชน์ (compound คุณประโยชน์), at the price of over-masking glued `คุณสามารถ…`. The lists also exclude the words that complete common names (ใจ, ขวัญ, ถึง, ดี, มา, มี, ต้อง). **Accepted residual: ยา.** It stays a ชื่อ thing-label so ชื่อยา… reads clean, but ยา is also an uncommon nickname (the common spelling is ญา): `ผู้ป่วยชื่อ ยา มาด้วยไข้` passes, and `ชื่อ ยา ใจดี` also leaves the surname in clear because the bare-surname slot is skipped once the label survives. `ชื่อเล่น ยา` is still masked. Any new list word must be checked against given names AND nicknames first; the adversarial name × template matrix in `pii-leak-adversarial.test.js` is the guard. **Cost bound:** a glued run longer than 256 chars skips the shields and is masked whole, as on master, which keeps the filter linear (an anonymous guest's history reaches it). /chat and /audit-discuss also cap each turn at 24000 chars (`rimpl/src/lib/turn-limits.js`, derived from `RIMPL_CHAT_MAX_TOKENS`), and so does the backend guest route. **Accepted narrowings:** (a) a lowercase or title-case English `line <word>` with no `:`/`id`/`@` marker and a word that is not id-shaped is no longer read as a LINE id (`Line somchai`; `LINE somchai`, `line somchai99` and `line: somchai` are still masked). (b) An all-lowercase word after `ward` (`ward sirindhorn`) is treated as prose. A quantifier (ต่าง/ทุก/หลาย/แต่ละ) never hides a following province; all 77 are tested. **Closed along the way:** the `ชื่อ X ผู้ป่วยชื่อ มานะ` label-swallowing leak (master), and the bare gazetteer name glued after ของ/กับ/ให้ (`แม่ของสมศรีโทรมา`, leaked on master). A non-gazetteer name in that position with no title (`แม่ของวิไลโทรมา`) is still the open bare-name gap above. Age masking is unchanged (open IRB question). /evaluate and /evaluate-criteria now run the PII strip inside their `try`, so a filter failure is a 500 rather than a process exit.
- **Impact:** PII *is* stripped before the outbound cloud call across the covered categories; the bare-name class is now closed for any name the physician entered at intake plus common gazetteer names.

## Social sign-in (Google/LINE OAuth) — GOOGLE LIVE, LINE ABSENT
- The **real Google handshake is now wired via Supabase's native provider** (updated 2026-06-09): the browser completes `signInWithOAuth({provider:'google'})`, the backend validates the session token server-side (`POST /auth/oauth/google/complete`) and writes the identity to the on-prem encrypted vault — the old mock-callback stub is gone. **LINE is still absent**: Supabase has no native LINE provider, so it needs a custom OIDC integration and remains a documented follow-up.

## "4 pre-filter signals" — NOT IMPLEMENTED
- The flowchart lists "Pre-filter 4 signals" at L3. No code defines or computes these four signals.
- What exists: a single retry loop in `rimpl/src/routes/chat.js` that re-prompts if the reply is missing a citation or a Socratic question.

## ELM injection — NOT IMPLEMENTED
- "Anti-sycophancy + ELM" appears in the flowchart. **Anti-sycophancy, zero-hallucination/citation, and Socratic-question** directives ARE injected (system prompt in `rimpl/src/lib/prompts.js`). **ELM** is referenced in the spec but never defined or implemented.

## Auth / fail modes (by design, documented)
- RIMPL guards `/chat`, `/evaluate`, `/evaluate-criteria` with an `x-internal-token` shared secret. **Hardened this cycle:** RIMPL now **refuses to boot in production** if `INTERNAL_TOKEN` is unset (`rimpl/src/index.js`), so it can never run unauthenticated on Railway. Local dev with no token still skips the check.
- Backend → RIMPL fail modes are intentionally asymmetric: `POST /ples/:id/message` **fails closed** (502 if RIMPL is down); `POST /ples/:id/end` Tier-2 check **fails open** (flags the session `ple_flag_t2` for manual QA).
- There is **no backend health-check** of RIMPL before routing (`/health/deep` is a possible future add).

## Reproducibility
- AI evaluations are tagged `CCME_LLM_v8.0` (`model_version`), but the underlying Claude model is pinned in code (`claude-sonnet-4-6`). If the model is swapped, re-run the Tier-2 calibration sample for drift (per the pilot protocol).
