# RIMPL Middleware — Known Gaps vs. the Architecture Flowchart

_The middleware **works end-to-end as a Claude-only pipeline** (PII masking → anti-sycophancy / citation / Socratic system prompt → Claude → post-checks). The items below are places where the current implementation is **narrower than the printed 4-layer flowchart**. They are documented intentionally._

> **Two framings in that sentence are out of date.** The "July–September 2026 pilot build" schedule is
> superseded — neither milestone started ([pilot-timeline.md](pilot-timeline.md)). And "the pilot
> decision is to run Claude-only" is now contradicted by the local-model programme: D8 moves every
> purpose on-premise and the CREC submission set forecloses a commercial external API for research
> transcripts ([LOCAL-MODEL-ROADMAP.md](LOCAL-MODEL-ROADMAP.md) D8/D17). Claude-only is what runs
> **today**, not the decision of record — which makes L4 below a gap to retire rather than to build._

## L4 — API Randomization Layer (multi-provider) — NOT IMPLEMENTED
- The flowchart shows L4 randomizing the AI provider per session across **Claude / GPT-4o / Gemini / Mistral** via `hashSessionId()`, with failover and `provider_used` logging.
- Reality: `rimpl/src/services/claude.js` hard-codes a single model (`claude-sonnet-4-6`) and is the only provider client. There is **no `hashSessionId()`, no GPT-4o/Gemini/Mistral client, no failover, and no per-session provider selection.**
- `ples.provider_used` exists in `db/schema.sql` but is a static default (`'claude'`), not a logged runtime choice.
- **Impact:** the privacy/bias rationale of vendor rotation is not exercised. All de-identified traffic goes to Claude.

## PII de-identification — BROADENED (2026-06-09); residual free-text-name risk
- `rimpl/src/services/pii-filter.js` is now a **multi-category de-identifier**: NAME (Thai/English title-led, labelled `ชื่อ…นามสกุล…`, nicknames, plus bare re-occurrences of already-seen names), EMAIL, LINE id, Thai national ID, HN, MRN/AN, PHONE (Thai + international), DATE, WARD, ADDR (house no. / หมู่ / ตำบล-อำเภอ-จังหวัด) — with **stable per-category indexed tokens** (`[NAME-1]`, `[HN-1]`, …) so repeated mentions collapse to one referent.
- It is complemented by a **structured patient-identifier intake**: `ple_patient_refs` (`db/migration-patient-intake.sql`) holds the patient identifier in a physically separate, **owner-only** table (deny-all RLS + route-layer physician filter) that is **never** read by the cloud-AI payload, the auditor blind queue, or the export — keeping the case narrative name-free by construction; the filter remains the backstop for anything typed into the narrative.
- The flowchart's **stable pseudonymization** is **partially built now**: `professionals.pseudonym` (P-NNN) is assigned at account creation/approval, and OAuth real identities are AES-256-GCM-encrypted in the deny-all `oauth_identities` vault (see [constraints.md](constraints.md)). The **PLE-001…PLE-150** session pseudonyms (Phase 2) and the **reversible on-prem token→value map** (`ple_pii_map`, 2026-06-18 — see below) now exist; in-message masks are recoverable for Tier-1 audit while staying de-identified everywhere else.
- **Bare-name leak — CLOSED (2026-06-18):** the once-residual unlabelled name (`สมชายมาด้วยไข้`) is now masked by two added layers: (1) an **intake-hint pass** — the backend forwards the physician's structured `patient_ref` (on-prem) to RIMPL on the chat + evaluate calls so those exact strings are scrubbed verbatim, even mid-sentence (`deriveHintTokens` in `pii-filter.js`); and (2) a conservative **Thai given-name gazetteer** backstop (`rimpl/src/services/pii-names.th.js`) that masks a common bare name at a boundary + clinical-lead/standalone, when no intake was entered. Both feed the existing `[NAME-n]` registry. **(3) a Chinese-Thai clan-surname pass (2026-06-22, `TH_SURNAMES` in `pii-names.th.js`)** masks `แซ่X` surnames VERBATIM in any position — the `แซ่` prefix is an unambiguous surname marker, so it closes the bare-surname-after-given-name leak (incl. the glued form `แซ่ลี้เข้ารับ…`) with no over-masking risk. NATIVE Thai surnames are deliberately NOT hand-seeded (they double as given/place/clinic/pharmacy names → would over-mask clinical text fed to PIS-7) and rely on the intake-hint layer or a future authoritative registry. `patient_ref` is scrubbed before any cloud call and never forwarded.
- **Reversible on-prem audit map — BUILT (2026-06-18):** at finalization RIMPL returns the de-id `[NAME-n]→raw` registry (on-prem only, never to cloud); the backend AES-256-GCM-encrypts it (`IDENTITY_ENC_KEY`) into `ple_pii_map` — one row per PLE, RLS **deny-all**. Tier-1 (superadmin/PI) re-identifies a token via the gated, **audit-logged** `GET /admin/ples/:id/pii-map` (`action: 'pii.reidentify'`); the export never reads it. Scoped **per-PLE** (no cross-session patient linkage by design).
- **New residual:** a bare name that is (a) NOT recorded in `patient_ref` AND (b) not in the given-name gazetteer / not a `แซ่` clan surname AND (c) not title/label-led still leaks (Thai has no word spaces → the gazetteers are best-effort; native surnames are intentionally left to the intake-hint layer rather than hand-seeded, since they collide with given/place/clinic names). The map covers only finalized (tier-1-passed) PLEs.
- **Bare ENGLISH personal name — OPEN (reported 2026-10-02 by the Phase 3 question-bank pass):** an English name with no honorific (`Dr`/`Mr`/`Mrs`/`Ms`/`Miss`/`Prof`), no `nickname` label and not recorded in `patient_ref` passes in clear — `John Smith presented with chest pain` is sent unchanged. There is **no English given-name gazetteer** (the Thai one is Thai-only), and capitalisation alone cannot separate a name from a sentence-initial word, a drug brand or an eponym (Murphy's sign, Parkinson). Mitigation today is the intake-hint pass: a name the physician recorded in `patient_ref` *is* scrubbed verbatim (`tests/pii-false-positives.test.js` proves it). Pinned as a `test.todo` in that file.
- **Clinical false positives — NARROWED (2026-10-02):** `คุณ…` (ขอบคุณครับ, คุณหมอ, คุณภาพ, the pronoun "you"), `เชื่อ`/`ชื่อ` + thing-labels (ชื่อยา, ชื่อโรค, ชื่อสามัญ, ชื่อการค้า), English `line` (first-line, joint line, IV line), `ward`/`toward`/`ward round`, and ต่างจังหวัด / รพ.สต. / รพ.จังหวัด were being masked, corrupting the text PIS-7 scores. Each rule now uses a closed shield list or a lookbehind, and anything the list does not account for is still masked (fail-closed). Accepted narrowings, kept deliberately small: (a) a lowercase or title-case English `line <word>` with no `:`/`id`/`@` marker and a word that is not id-shaped (no digit, `_` or dotted segment) is no longer read as a LINE id (`Line somchai`; `LINE somchai`, `line somchai99` and `line: somchai` are still masked). (b) An all-lowercase word after `ward` (`ward sirindhorn`) is treated as prose. Age masking was intentionally left byte-identical (open IRB question). The change also closed a pre-existing leak: `ชื่อ X ผู้ป่วยชื่อ มานะ` used to leave `มานะ` in clear.
- **Impact:** PII *is* stripped before the outbound cloud call across the covered categories; the bare-name class is now closed for any name the physician entered at intake plus common gazetteer names.

## Social sign-in (Google/LINE OAuth) — GOOGLE LIVE, LINE ABSENT
- The **real Google handshake is now wired via Supabase's native provider** (updated 2026-06-09): the browser completes `signInWithOAuth({provider:'google'})`, the backend validates the session token server-side (`POST /auth/oauth/google/complete`) and writes the identity to the on-prem encrypted vault — the old mock-callback stub is gone. **LINE is still absent**: Supabase has no native LINE provider, so it needs a custom OIDC integration and remains a documented follow-up.

## "4 pre-filter signals" — NOT IMPLEMENTED
- The flowchart lists "Pre-filter 4 signals" at L3. No code defines or computes these four signals.
- What exists: a single retry loop in `rimpl/src/routes/chat.js` that re-prompts if the reply is missing a citation or a Socratic question.

## ELM injection — NOT IMPLEMENTED
- "Anti-sycophancy + ELM" appears in the flowchart. **Anti-sycophancy, zero-hallucination/citation, and Socratic-question** directives ARE injected (system prompt in `rimpl/src/lib/prompts.js`). **ELM** is referenced in the spec but never defined or implemented.

## Auth / fail modes (by design, documented)
- RIMPL guards `/chat`, `/evaluate`, `/evaluate-criteria` with an `x-internal-token` shared secret. **Hardened this cycle:** RIMPL now **refuses to boot in production** if `INTERNAL_TOKEN` is unset (`rimpl/src/index.js`), so it can never run unauthenticated on Railway. Local dev with no token still skips the check.
- Backend → RIMPL fail modes are intentionally asymmetric: `POST /ples/:id/message` **fails closed** (502 if RIMPL is down); `POST /ples/:id/end` Tier-2 check **fails open** (flags the session `ple_flag_t2` for manual QA).
- There is **no backend health-check** of RIMPL before routing (`/health/deep` is a possible future add).

## Reproducibility
- AI evaluations are tagged `CCME_LLM_v8.0` (`model_version`), but the underlying Claude model is pinned in code (`claude-sonnet-4-6`). If the model is swapped, re-run the Tier-2 calibration sample for drift (per the pilot protocol).
